# Trackside — Secrets and environment keys

## Rules this repository follows

| Rule | How |
|---|---|
| No secret in source code | Every secret is read from the environment (`config/settings.py` uses `django-environ`; firmware keys live in `radio_secrets.h`, which is ignored by git). Checked by a full scan of the files and the git history. |
| Secrets only on the server | The backend reads them; the browser never receives one. |
| `.env` files never committed | `.gitignore` ignores `.env`, `.env.local`, `.env.production`, `.env.docker` and every other `.env.*` (only `*.example` templates are committed), plus `radio_secrets.h` and `*.sqlite3`. |
| Templates hold placeholders only | `.env.example`, `.env.production.example`, `backend/.env.example`, `demo/.env.example`, `frontend/.env.example`, `firmware/*/radio_secrets.h.example` (all-zero keys). |
| Placeholders can never run in production | With `DJANGO_ENV=production` the server refuses to start when `SECRET_KEY` is empty, shorter than 32 characters, repetitive, or still contains placeholder text (`config/secret_checks.py`). SQLite is refused in production. The first admin (`seed_admin`) must pass the password rules. |
| Separate development and production credentials | Development uses `backend/.env` (SQLite, a local key). Production values are set only in Render's **Environment** or the server's `.env` from `.env.production.example`, each generated fresh. |

## Where each secret lives

| Secret | Development | Production |
|---|---|---|
| `SECRET_KEY` (Django signing) | `backend/.env` | Render: generated by the Blueprint. Docker: `.env` |
| `DATABASE_URL` / `POSTGRES_PASSWORD` | not needed (SQLite) | Render: linked database. Docker: `.env` |
| `REDIS_PASSWORD` | not needed | Docker: `.env` |
| `ADMIN_PASSWORD` (first admin only) | `backend/.env` | set once, then **deleted** from the environment |
| Device tokens (`dt_…`) | shown once when the admin adds a device | the same; only a SHA-256 hash is stored |
| Laptop-link token | shown to the coach for the laptop's `demo/.env` | the same; never in the page URL |
| ESP-NOW radio keys (PMK/LMK) | `firmware/*/radio_secrets.h`, made by `firmware/tools/make_radio_keys.py` | the same file, kept off git |

## Browser (`VITE_`) variables

Everything named `VITE_` is built into the public JavaScript, so none of these may hold a secret:
`VITE_ENABLE_DEMO_TOOLS`, `VITE_ACADEMY_NAME`, `VITE_MAP_TILE_URL`, `VITE_MAP_ATTRIBUTION`, `VITE_MAP_MAX_ZOOM`.

The default map (OpenStreetMap) needs no key. If a satellite provider is used, its key ends up in
`VITE_MAP_TILE_URL` and is visible to every visitor. Map providers design these browser keys to be public:
**restrict it to your site's address at the provider** (see `RENDER.md`, "Real map"), or don't use one. Any key
that is not meant to be public must go through a backend endpoint instead.

## Scanning before submission

```bash
# from the repository root: secret-looking assignments in files and in every past commit
git grep -n -I -E "(SECRET_KEY|PASSWORD|TOKEN|API_KEY)\s*[=:]\s*['\"]?[A-Za-z0-9!@#%^&*_+./-]{8,}" -- . ':!*/tests/*' ':!*e2e/*'
git log --all -p | grep -E "^\+.*(SECRET_KEY|PASSWORD|TOKEN|API_KEY)\s*[=:]"
```

Only placeholders (`replace-me…`, `change-this…`) and throw-away test passwords inside the automated tests
should appear. Test passwords only ever exist in temporary test databases.

## If a secret was exposed

Rotate it at once; deleting it from a file or a chat does not make it secret again:

- `SECRET_KEY`: set a new value in Render / `.env` and redeploy (everyone signs in again).
- A user's password: the admin sets a new one in the user editor.
- A device token: delete and re-add the device, then put the new token on the board.
- Database or Redis password: change it at the provider and in the environment together.
- Radio keys: run `make_radio_keys.py` again and reflash both boards.
